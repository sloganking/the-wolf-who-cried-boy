## mdBook Production & Formatting (added 2026-07-07)

- [ ] **Audit a production-grade mdBook for formatting/presentation techniques we're not using.** The author flagged [*The Rust Programming Language*](https://doc.rust-lang.org/book/) — the official Rust book — as a mature, widely-used mdBook build worth studying. It's the same tool this book uses (`book.toml` at repo root), built to a high production standard. Task for an agent with web access: read through the Rust book's rendered pages and (ideally) its source, and catalog the mdBook features/conventions it uses that this book doesn't yet — callout/admonition boxes, code-block annotations and highlighting, collapsible sections, the search index config, theme customization, keyboard-shortcut help, cross-reference/footnote patterns, any custom preprocessors or plugins declared in its `book.toml`. Produce a list of candidates with a one-line take on whether each would add value here (this book has no code blocks, so code-highlighting techniques don't transfer, but callout boxes, admonitions, and navigation/theme polish likely do). Then decide with the author which to adopt.

- [ ] **Replace or upgrade the ASCII-art diagrams — author-flagged, connects to the item above.** The book uses code-fenced (```` ``` ````) blocks for diagrams and lists in six files. Two problems, the author's own: (1) **AI readers parse them badly** — an LLM reading the book (a real audience: readers pasting chapters into a chat, future AI co-authors, accessibility tools) sees a fenced code block and treats it as literal/verbatim content rather than a diagram, and box-drawing characters (`┌─┐│└┘`) don't reliably survive copy-paste, narrow viewports, or text-to-speech; (2) **they're not pretty** — hand-drawn box art in a monospace font is the opposite of the production polish the rest of the book has. The author wants real charts/diagrams in the finished book (cutting them isn't the goal) — the question is the right format for each. Two different problems, two different fixes:
  - **Genuine spatial/flow diagrams — candidates for real rendered diagrams (SVG, or a mermaid.js-style mdBook plugin if the Rust-book audit above finds one), not plain text:**
    - `trauma-and-filters.md` (~line 14) — Experience → Story → Feelings, three connected boxes
    - `body-stories.md` (~line 115) — same pipeline, simpler arrow-only version (near-duplicate of the above — resolve which is canonical)
    - `types-of-mistakes.md` (~line 92) — the 2×2 Intentional/Unintentional × Conscious/Unconscious matrix (this one's actually a table — consider a real Markdown table instead of a diagram)
    - `appropriate-response.md` (~lines 13, 40, 153) — the severity/response spectrum, the unqualified-response flow, and the mistake-occurs decision tree
    - `fawning.md` (~lines 47, 90) — the boxed "Fawning Dynamic" diagram and its simplified arrow version (also near-duplicates — same resolve-canonical question)
  - **Plain lists/text dressed up in a code fence for a monospace look — these should just become normal Markdown (numbered lists, bold, or a table), no diagram needed:**
    - `quick-reference.md` (~line 80) — the 6-step PAUSE/SEVERITY/TYPE/... list is already a numbered list; the code fence adds nothing but bad copy-paste behavior
    - `before-play.md` (~lines 487, 568) — the "BEFORE INTIMACY, ASSESS" and "BEFORE PLAY, DISCUSS" (RBDSMT) blocks are label/description pairs — natural fit for a two-column Markdown table
    - `types-of-mistakes.md` (~line 264) — the conscious/unconscious `████░░░░` bar — could stay visual (a described percentage, or a simple table: "Conscious: 40% / Unconscious: 60%") without block-drawing characters
  - **Decide with the author:** which diagrams are worth real graphics (likely candidates: the Story pipeline, the Fawning Dynamic, the decision-tree flow — these carry real teaching weight) vs. which should just be simplified to text/tables. Check the mdBook audit above first — it may reveal a supported diagramming approach (e.g., a mermaid preprocessor) that renders cleanly AND stays as readable source text for AI readers, which would be the best of both.

## Final Passes (Quick — Do Right Before Publishing)

These are fast sweeps across the whole book. Each takes 15-60 minutes. Run them as final checks even if you think you've already fixed everything.

- [ ] **"Demanding" language sweep** — Search for "demand," "demanding," "insist" when used to describe what the reader should do. Replace with "ask for," "advocate for," "request." The book teaches consent and collaboration, not coercion — even when advocating for yourself.
- [ ] **Video/link attribution** — Every YouTube link and external reference should include the creator's name so it makes sense in print (e.g., "Destin Sandlin, *Smarter Every Day*"). Search for `youtu` and `http` to find them all.
- [ ] **Navigation typo sweep** — Search for "←←" (double arrows). Known instances in `before-you-facilitate.md`, `when-things-go-wrong.md`, `guiding-public-repair.md`.
- [ ] **Identity label sweep** — Search for "bad person," "good person," "evil," "monster," "predator" used as identity labels rather than behavioral descriptions. The book teaches describing behavior, not labeling character.
- [ ] **"There's nothing you can do" / powerlessness sweep** — Search for language that counsels acceptance or powerlessness before the reader has been told to advocate. No page should tell the reader they're helpless before asking: have you actually requested what you want?
- [ ] **Quotes audit** — Verify all quoted sources add value. Check distribution of who's being quoted. Remove any that are redundant or weaker than the author's own language.
- [ ] **No real names in personal examples** — Scan all narrative examples and personal stories for real names. Quote attributions (Laurie Handlers, Tony Robbins, etc.) are fine. Names placed as characters in stories about conflict, harm, or failure are not. All such stories should use roles ("a facilitator," "a participant," "a friend"), not names. See writing-guide.md anti-pattern for the full rule.
- [ ] **Print readability** — All hyperlinks should make sense without clicking. If a link says "this tool" or "here," the surrounding text should explain what it links to. Paper readers can't click.
- [ ] **"Character assassination" sweep** — Replace all instances with "attacking their reputation" or "publicly attacking their reputation." "Character assassination" is wound language — narrative, arguable, dramatic. Describe the behavior instead.
- [ ] **Stub section sweep** — No section header should exist for only 1-2 lines of content. Either merge the content into the preceding section, expand it, or remove the header and keep the text as a closing paragraph.

Go through the page and (1) cut lines that read well but aren't lessons he really teaches — watch especially the later sections, which came from weaker extraction candidates; (2) add any line he says at every workshop that's missing (if it's not in a chapter yet, add it to the chapter first — every entry must appear verbatim in the book); (3) keep the arc order.
